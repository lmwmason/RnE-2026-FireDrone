# FireDrone X8 — USB 조종기 / 앵글 모드

기본 실행은 **Taranis X9D Plus USB 조이스틱으로 직접 조종하는 실시간 시뮬레이터**입니다.
기본 경로에는 웨이포인트 자율주행이 없습니다. 롤·피치 스틱은 최대 35°의 목표 기울기,
요 스틱은 회전 속도(최대 180°/s), 스로틀은 추력을 지정합니다. 스틱 중립은 UKF 추정 자세를
기준으로 수평을 목표로 합니다. 높이/위치를 자동 유지하지 않습니다.

## 실행과 조종기 보정

```bash
./run.sh                     # 기본: 3D 외부 시점 + 계기판, 랜덤 고장 ON, 로봇팔 계속 동작
./run.sh fpv --list-devices   # USB 장치 확인
./run.sh fpv --seed 123      # 재현 가능한 랜덤 시드
```

X9D Plus를 USB **조이스틱 모드**로 연결한 뒤 창에서 `C`를 누릅니다.
화면 안내대로 중립/스로틀 최저 → 롤 오른쪽/왼쪽 → 피치 앞/뒤 → 요 오른쪽/왼쪽 → 스로틀 최고를
입력하고 각 단계에서 Enter를 누릅니다. 채널 순서·방향·중립·끝점을 직접 측정하므로 AETR/TAER를
임의로 가정하지 않습니다. 프로필은 `out/joystick/<USB GUID>.json`에 저장합니다.
4축 미만의 가상 마우스는 조종기로 선택하지 않습니다. 현재 실제 X9D 연결 시험은 아직 하지 않았습니다.

| 키 | 동작 |
|---|---|
| `Space` | 스위치 미지정 시 시동 ON/OFF. 스위치 지정 시 강제 OFF(스위치를 다시 OFF→ON 해야 재시동) |
| `B` | 조종기의 버튼 또는 사용하지 않는 축을 시동 스위치로 지정. 지정 후 OFF→ON 필요 |
| `V` | 외부 3D 계기판 ↔ FPV 시점 전환 |
| `C` | 채널 보정(보정 중 시뮬레이션 일시정지) |
| `F5` | 새로운 랜덤 고장 주입 ON/OFF. 이미 발생한 손상은 복구하지 않음 |
| `P` | 일시정지/재개, 시동 요청 해제 |
| `R` | 새 기체로 시험 재시작, 시드 +1. 비행 중 부품 자동 복구 없음 |
| `Esc` | 종료 |

조종기 분리/입력 만료 시 마지막 스틱 값을 계속 사용하지 않고, 추정 자세로 수평화하고 기압계로
하강하는 failsafe로 전환합니다. 이는 웨이포인트 주행이 아닙니다. 재연결 직후 스위치가 이미 ON이면
자동 시동하지 않습니다. 창이 포커스를 잃으면 일시정지합니다.

기본 화면은 왼쪽에 X8·로봇팔 3D 외부 시점, 오른쪽에 최근 30초 고도/롤/피치/팔 각도와 8개 모터 출력을 표시합니다.
황색 세로선은 고장 주입 시각입니다. `./run.sh fpv --view fpv`로 FPV 화면부터 시작할 수 있습니다.
외부 시점 격자는 기체를 따라가는 0.5 m 기준 격자이며 지면이 아닙니다. 프롭 반경과 상하 모터 간격은 시각화 가정입니다.

## 무작위 극한 상황과 로봇팔

- 시동 후 첫 고장은 5–12초 사이, 이후 5–15초 간격의 무작위 시각에 발생합니다.
- 바람/돌풍, 프롭 손상, 모터 정지, 가속도 고정, 자이로 바이어스, 가속도 충격, RC 단절,
  GPS 단절, 짧은 IMU 전송 단절을 중복 없는 무작위 순서로 주입합니다.
- 10번째 이벤트는 모든 고장을 동시에 주입합니다. 이때는 IMU 완전 단절도 3초 지속됩니다.
  살아 있다면 다음 주기가 계속됩니다. 추락하면 정지하고 `R`로 새 시험을 시작합니다.
- 모터와 프롭 손상은 누적됩니다. 뒤의 '개별 고장'에는 앞선 영구 손상이 남아 있으므로
  독립된 단일 고장 시험과 동일하지 않습니다.
- 로봇팔은 0.8–3초마다 무작위 목표각을 받고, 속도·가속도 제한을 거쳐 계속 움직입니다.
  화면의 팔은 실제 모델의 관절각이며, 토크를 화면용 각도로 임의 환산한 것이 아닙니다.
- 비행 기록은 `out/fpv_<시각>.csv`, 기체 설정/시드 정보는 같은 이름의 JSON에 저장됩니다.
  CSV에는 재시작별 flight/seed, 스틱 입력, 실제 자세, 8개 모터 명령/효율, 팔 각도/토크를 남깁니다.

## 물리 모델과 제어 코드의 경계

`src/physics.c`의 강체 운동식, 중력, 항력, 모터 지연, quaternion 적분, RK4 적분법은 유지했습니다.
X4 고정 합산을 모터별 위치/회전 방향을 입력받는 4/8개 합산으로 확장했습니다.
기본 배치는 **팔 4개 × 상하 2개 동축 X8**입니다. 위 M1–M4는 뒤오른쪽/앞오른쪽/뒤왼쪽/앞왼쪽,
아래 M5–M8은 같은 팔에 반대 회전으로 놓입니다. 실제 모터 번호/회전 방향 확정 시 설정을 맞춰야 합니다.

- `flight_core/control.c`: 보드 독립 C99 제어. 수동 앵글 루프 → 기존 UKF/ADRC/MRAC 모듈 +
  8모터 증분 역변환(INDI) → 제한이 있는 CAM 할당. 모터 정지는 ESC RPM 관측값으로 감지합니다.
- `flight_core/allocator.c`: 8모터 제한 최적화. 고장 모터 출력 0, 나머지 출력 0–1 범위를 보장하며
  달성 불가능한 힘/토크는 잔차로 남깁니다. 모터 하나가 죽었다고 무조건 yaw 제어를 끄지 않습니다.
- `src/live_sim.c`: 물리/센서/환경 모델과 제어 코드를 연결합니다. 실제 자세, 모터 고장 마스크,
  실제 외란 토크를 정답으로 제어기에 전달하지 않습니다. USB 입력은 교정한 RC 채널로 전달합니다.
- 제어 주기 1 ms, 물리 적분 0.5 ms. 렌더링이 느려져도 물리 dt를 늘리지 않으며 화면에 속도 저하를 표시합니다.
- `build/h7-core/libfiredrone.a`: 같은 제어 소스를 Cortex-M7 대상으로 크로스 컴파일한 라이브러리입니다.
  **H7 보드용 완성 펌웨어/플래시 이미지가 아닙니다.** MCU, 핀, 타이머, 센서/ESC 전송 LL 드라이버는 미정입니다.

## 추가 점검에서 수정한 오류

- GPS 단절 중 새 위치/속도 유입 차단, 마지막 유효 샘플 시각 유지. 모터 진단의 고도 조건은 유효한 기압계 사용.
- 시동 해제 시 모터 할당과 ADRC/MRAC 상태 정리, 해제 중에도 자이로 미분 필터 갱신.
- 비정상 가속도만 들어온 경우 정상 자이로까지 전체 고장으로 취급하지 않도록 분리.
- NaN 기압계, 범위 밖 RC 프레임, 초기화되지 않은 제어기/할당기, 불가능한 질량/관성 설정 거부.
- 조종기 스위치가 키보드 해제를 덮어쓰던 경로 수정, USB 분리 시 보정/스위치 지정 상태 해제.
- 로봇팔 난수와 고장 난수 분리. 고장 ON/OFF가 같은 시드의 팔 움직임을 바꾸지 않음.
- 실행 중인 프로그램의 공유 라이브러리를 직접 덮어쓰지 않고 빌드 완료 후 원자적으로 교체.
- 로그에 연결/고장 주입/일시정지 상태, 제어 불능, 진단 마스크 추가. JSON에 바이너리 해시와 보정 프로필, 재시작별 설정 기록.

## 아직 검증되지 않은 실제 기체 항목

사용자가 확정한 것은 동축 X8, H7 계열, 10인치 프롭 계획입니다.
`configs/x8_design_study.conf`의 질량 2.5 kg, 관성, 추력, 모터 지연, 팔 질량/길이는 모두
**설계 시험용 가정값**입니다. 실측 검증 결과로 읽으면 안 됩니다. `upper_gain/lower_gain=1`은
동축 간섭이 보정되지 않았다는 뜻이며, 실제 프롭의 동축 공력·배터리 전압 변화·추력 곡선은 아직 없습니다.

로봇팔은 단일 링크의 축약 반작용 외란 모델입니다. `J=mL²/3`,
`tau_body=-(J*관절가속도 + m*g*L/2*sin(관절각))`를 사용하며, 기체 병진/회전과 팔 사이의
완전한 다물체 결합은 포함하지 않습니다. 총질량에는 팔 질량을 포함한 것으로 가정합니다.
기존 기체 운동식을 합격을 위해 완화하거나 추락을 강제로 복구하지 않습니다.

PDF의 Robot Arm FF용 타임스탬프 토크 추정 입력과 stale 검사/증분 보상 경로는 구현되어 있습니다.
그러나 팔 엔코더/명령 인터페이스와 식별값이 없어 **실행 시 FF는 비활성**입니다.
실제 외란 토크를 그대로 넣어 완벽한 FF인 것처럼 만들지 않았습니다.
단일 IMU가 완전히 끊긴 뒤 20 ms를 넘기면 제어 불능으로 기록합니다. 백업 센서 없이
모든 센서 고장을 극복했다는 주장은 하지 않습니다. UKF는 현재 자세/각속도용이고, 고도는 별도
기압계 필터입니다. PDF의 고도 UKF와 MRAC '수십 ms 적응' 목표도 달성 검증되지 않았습니다.

# 기존 X4/F405 SITL 기록

STM32F405 비행 펌웨어(`drone-f405-foxeer-firmware`)를 **수정 없이 그대로** 호스트에서 돌리고,
C 물리엔진에 붙여 닫힌 루프로 비행시키는 시뮬레이터입니다. (펌웨어 소스는 이후 `patches/`의 수정이 반영된 상태입니다. "수정 없이"는 시뮬레이터가 펌웨어를 고치지 않고 컴파일한다는 뜻입니다.) 시각화·채점은 Python입니다.

> 슬라이드의 임베디드 파트(UKF → INDI/ADRC/MRAC → CAM + Fault FSM)가 강풍·센서 고장·통신 두절·
> 프로펠러 손상에서 실제로 비행하는지 확인하는 것이 목적입니다.
> **결과 요약: 펌웨어 원본은 이륙 후 2초 안에 발산합니다. 원인을 분리해 패치 7개로 고쳤고(펌웨어에 반영됨),
> 9개 시나리오가 통과합니다. 남은 한계(모터 고장 회복 불가, 수평 드리프트, 최악 틱 98 %)는 [FINDINGS.md](FINDINGS.md)에 정리했습니다.**

## 실행

```bash
./run.sh all              # 빌드 + 9개 시나리오 × 5개 빌드 + 리포트  (out/summary.md, out/comparison.png)
./run.sh view gust        # 3D 재생 (matplotlib 창)
./run.sh video extreme    # out/extreme.mp4 렌더 (ffmpeg 필요)
                          # prop_damage / arm_swing / extreme은 기체를 따라가는 근접 카메라가 기본 (--wide로 전체 보기)
./run.sh timing           # Cortex-M4 사이클 예산 (pip install unicorn capstone)
make distclean            # 빌드 산출물 + out/ 삭제
```

`unicorn`이 없어도 MCU 연산시간 반영 열은 `timing/reference/`에 저장된 측정값으로 돌아갑니다.

개별 실행:

```bash
make all
./firedrone_sim --list
./firedrone_sim --scenario gust --out out/gust.csv
./firedrone_sim --scenario extreme --cost-us 421,978     # MCU 연산 시간 반영 (-O2)
./firedrone_sim --scenario extreme --att ukf           # 자세를 펌웨어 UKF에서 받음
./firedrone_sim_orig --scenario nominal                # 수정 전 펌웨어
python3 scripts/visualize.py --build patched --scenario gust --orbit
```

필요한 것: `gcc`, `make`, `python3` (numpy, pandas, matplotlib), `ffmpeg`(영상), `arm-none-eabi-gcc` +
`unicorn` + `capstone`(MCU 타이밍, 선택).

## 구조

```
 Python (scripts/)                C (src/)                                 펌웨어 (수정 없음)
 ┌─────────────┐   CSV    ┌─────────────────────────────┐
 │ analysis.py │◄─────────│ physics   6-DOF RK4, 모터 lag │   shim/ : HAL/LL 대체 (TIM CCR 레지스터는
 │ visualize.py│          │ environment 바람·돌풍          │            실제 메모리 → PWM을 그대로 읽음)
 └─────────────┘          │ sensors   IMU(ICM-42688)·nav │        ▲
                          │ scenario  고장 주입 이벤트      │        │
                          │ pilot     미션 → 스틱(CRSF)   │   ┌────┴─────────────────────────────────┐
                          │ fw_host ───────────────────────┼──►│ Core/Src/main.c  (1 kHz 슈퍼루프 그대로)  │
                          └─────────────────────────────┘   │ UKF  INDI  ADRC  MRAC  CAM  fault FSM    │
                                                            │ CRSF 파서, motor.c (TIM1/8 PWM)          │
                                                            └──────────────────────────────────────────┘
```

- **펌웨어가 도는 방식**: `fw_host.c`가 `main.c`를 `#include`하고 `main`→`fw_main` 이름 변경,
  슈퍼루프의 `while(1)` 조건에 "호스트로 양보"를 끼워 넣습니다(전처리기 수준 2줄). 호스트가
  1 ms마다 센서값을 넣고 TIM6 플래그를 세우면 루프가 정확히 한 바퀴 돕니다. 레지스터 수준은
  `motor.c`가 쓰는 `TIMx->CCRn`, RC는 ELRS처럼 **CRSF 프레임(CRC8 포함)을 만들어 UART 콜백으로**
  넣기 때문에 파서·failsafe 타이머도 실제 코드가 돕니다.
- **교체한 것은 트랜스포트 드라이버뿐**: `imu/baro/gps` (SPI/I2C/UART). 그 위는 전부 원본.
- **좌표계**: 월드 ENU, 기체 FLU. 모터 순서·회전 방향·G 행렬 부호를 펌웨어(`indi.c`, `cam.c`)와
  맞췄고, 자이로는 펌웨어의 CW270 정렬에 맞춰 센서 프레임으로 내보냅니다.
- **상위 제어는 `pilot.c`**: 펌웨어는 각속도 루프만 닫습니다(스틱 = 각속도 지령). 그래서 웨이포인트
  미션을 스틱으로 바꿔 CRSF로 보내는 외부 자세/위치 루프를 시뮬레이터가 맡습니다.
  (자세 기본값은 UKF입니다. `--att truth`는 진단용으로만 사용합니다.)

## 시나리오 (`src/scenario.c`)

| 이름 | 내용 |
|---|---|
| `nominal` | 무풍, 정상 기체 (미션: 이륙 → 4개 웨이포인트 → 착륙) |

| `motor_fail` | M2 정지 |

## 한계 (이 시뮬레이터가 증명하지 못하는 것)

- 기체 모델은 펌웨어 상수(arm 80 mm, K_THRUST 5, I 등)에서 역산한 **가정**입니다 (질량 0.45 kg,
  모터 시정수 25 ms, 실제 값과 ±8~10 % 어긋나게 설정). 실기 리그에서 시정수·추력 곡선을 측정하면
  `src/physics.c`의 `DRONE_PARAMS` 한 곳만 바꾸면 됩니다.
- 사이클 수는 명령어 에뮬레이션 + Cortex-M4 TRM 표 기반 **추정**입니다. 플래시 대기 상태·DMA 경합·
  I2C/SPI 전송 시간·`task_50hz_baro`는 포함하지 않습니다. 1 kHz 태스크만 잽니다.
- 호스트(x86) float 연산과 MCU(FPv4-SP)의 libm 결과는 비트 단위로 같지 않습니다.
- LIV/VLA 분산 추론(AI 파트)은 범위 밖입니다. 통신 두절은 RC 링크 관점만 다룹니다.
